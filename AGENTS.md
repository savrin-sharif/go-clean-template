`go-clean-init.sh`. Agents that support `AGENTS.md` load this file
automatically; for other tools, paste it before your feature request and API

access to the project files.

## First: understand this project

Before changing anything:

1. Read `README.md`, `go.mod`, `.golangci.yml`, and the relevant files under
   `cmd/`, `internal/`, and `api/`.
2. Inspect `.env` / `.env.example`, but never expose secrets or commit real
   secrets.
3. Confirm the generated module path from `go.mod`; never assume it is
   `github.com/savrin-sharif/go-clean-template`.
4. Inspect `internal/config`, `internal/apperr`, `internal/logging`,
   `internal/httpserver`, and `internal/app`.
5. Identify whether the project uses the local or Postgres welcome repository
   from `DATABASE` / `DATABASE_URL`. Preserve that choice unless the request
   explicitly changes it.
6. Inspect the closest existing feature and follow its naming, imports,
   repository, use-case, handler, and testing conventions.
7. Check the current Git diff before editing. Preserve unrelated user changes.

Do not replace Gin with another router, introduce a second HTTP framework, add
Wire/fx unless requested, or invent a competing architecture. Do not add a
second SQL driver or ORM alongside the project's chosen data access style.

## Architecture contract

The project uses feature-first clean architecture:

```text
cmd/server/                 # Process entry point only
internal/
├── app/                    # Composition root (DI)
├── config/                 # Environment selection
├── apperr/                 # Typed Error hierarchy
├── logging/                # slog setup and redaction
├── httpserver/             # Server, middleware, JSON helpers
└── features/<feature>/
    ├── data/               # Repository implementations
    ├── domain/             # Entities, contracts, use cases
    └── http/               # Handlers and route registration
```

Dependencies point inward:

```text
http ──> domain <── data
  │         │
  └──── core packages (apperr, config types as needed) ─────┘
```

- Domain must not import Gin, SQL drivers, `godotenv`, OpenAPI generators, or
  data-layer packages. Domain may use the standard library and `apperr`.
- Data implements domain repository contracts.
- HTTP handlers call use cases, not SQL or raw config construction directly.
- Register concrete implementations only in `internal/app`.
- Keep genuinely one-off transport DTOs next to handlers; keep domain entities
  free of JSON tags unless the project already does otherwise.

## REST API rules

Gin is the only HTTP framework. Shared middleware lives in `internal/httpserver`.
Add cross-cutting auth through the `AuthHook` middleware (or a replacement
registered beside it in `NewEngine`), not inside every handler. Use the
constructed `*slog.Logger` for diagnostics; do not introduce ad-hoc `fmt.Println`
in request paths.

Environment behavior:

- `APP_ENV` resolves to `local`, `dev`, or `prod`.
- `DATABASE_URL` empty → local/in-process repositories for features that support
  them (welcome uses config-backed data).
- `DATABASE_URL` set → composition root may open Postgres via `pgx` and wire
  database-backed repositories.
- Never hardcode hosts inside feature data sources; read them from config.

Before implementing an API, obtain or discover:

- Endpoint paths and HTTP methods
- Request body/query/path parameters
- Success status codes
- Exact response envelope and JSON fields
- Pagination shape, if any
- Authentication mechanism and token source
- Validation/error response shapes
- Whether delete returns content, `204`, or a soft-deleted object

If these details are not in the request, repository, OpenAPI file, or provided
examples, ask concise questions. Do not invent production schemas.

### Handlers and responses

Use `httpserver.WriteJSON` and `httpserver.WriteError`. Success bodies use:

```json
{ "data": { ... } }
```

Error bodies use:

```json
{
  "error": {
    "kind": "validation",
    "message": "Validation failed.",
    "field_errors": { "email": "required" }
  }
}
```

Handlers must not invent status codes ad hoc. Map domain/data failures through
`apperr` so `WriteError` chooses the status.

### Models and entities

- Domain entities express business meaning.
- Transport DTOs own JSON field names at the HTTP boundary.
- Data models own SQL scanning / row mapping.
- Do not put `gin.Context`, `*sql.DB`, or JSON maps in entities.
- Separate create/update input types when required fields differ.

### Repository and failure behavior

Define repository interfaces in domain and implement them in data. Repository
methods return domain entities, never Gin contexts or raw HTTP responses.

`internal/apperr` defines typed errors:

- `validation` (field errors) → 422
- `unauthorized` → 401
- `forbidden` → 403
- `not_found` → 404
- `conflict` → 409
- `data` → 400
- `internal` → 500 (client message is always safe; cause stays wrapped)

Repositories may return `*apperr.Error` directly. Unexpected errors should be
wrapped with `apperr.WrapInternal`. Do not parse error strings in handlers.

## CRUD feature design

Use focused use cases, for example:

```text
ListItems
GetItem
CreateItem
UpdateItem
DeleteItem
```

Prefer explicit operation names over a single god-service. Preserve existing
successful behavior while a mutation runs. Choose concurrency deliberately for
handlers that can race (idempotent deletes, unique constraints → `conflict`).

For create/update/delete success:

- Create: return the server-authoritative entity
- Update: replace by stable ID
- Delete: confirm success before claiming deletion; use `204` when the API
  contract says so

## HTTP and middleware rules

- Handlers stay thin: decode, call a use case, map the result to HTTP.
- Validate local request syntax in handlers or a small decoder helper; domain
  validates business rules.
- Never show user-facing side effects (emails, pushes) inside repositories
  unless that is an explicit infrastructure adapter behind an interface.
- Provide health/live endpoints for probes.
- Prevent duplicate destructive submissions at the API contract level when
  needed (idempotency keys, unique constraints).
- Ask for confirmation is a client concern; the API still enforces authorization.

## Frontend

This is an API template. The embedded HTML welcome page (`/`) and Swagger UI
(`/docs`) are intentional and should be kept in sync with `api/openapi.yaml`.
Do not add HTML UI kits or SPA frameworks unless the user explicitly requests a
separate frontend.

## Dependency injection and routing

Register dependencies in `internal/app.New` from the outside inward:

```go
repo := data.NewLocalRepository(cfg) // or Postgres when configured
uc := domain.NewGetWelcomeInfo(repo)
welcomehttp.NewHandler(uc).Register(api)
```

- Data sources/repositories/use cases are usually long-lived for the process.
- Handlers are usually constructed once at startup.
- Add routes beside existing feature registration in `internal/app`.
- Pass IDs through path parameters and short filters through query parameters.

## Authentication, security, and logging

If authentication is requested:

- Discover any existing token validation first.
- Implement it in middleware (replace `AuthHook`), not in every handler.
- Never log access tokens, refresh tokens, passwords, authorization headers, or
  secret response bodies. `logging` redacts keys containing `token`, `password`,
  `secret`, `apikey`, `authorization`, or `cookie`. Do not weaken this
  redaction; add a key pattern if an API uses another secret name.
- Do not commit real secrets in `.env`.
- Treat client-side authorization checks as nonexistent; the server remains the
  authority.

## Testing requirements

Implement tests proportional to the change. For CRUD work, include:

1. Domain use-case tests with fake repositories
2. Data repository tests (fakes, sqlmock, or testcontainers when justified)
3. Handler tests with `httptest` and Gin test mode
4. `apperr` / `WriteError` mapping tests for the statuses the feature uses
5. Config tests when new env keys are introduced

Tests must assert meaningful status codes and JSON shapes, not only that a
handler exists. Use fakes at architectural boundaries; do not call live
production APIs.

## Execution workflow

For each request:

1. Restate the concrete outcome briefly.
2. Inspect the relevant existing implementation and API information.
3. Identify missing API-contract details; ask only blocking questions.
4. Make a small implementation plan for non-trivial CRUD work.
5. Implement vertically: domain → data → app wiring → HTTP → tests.
6. Format changed Go files (`gofmt` / `make fmt`).
7. Run `go test ./...` (and `make lint` when available).
8. Fix failures caused by the change. Do not suppress legitimate lints.
9. Report changed behavior, important assumptions, tests run, and any remaining
   external dependency such as an unavailable database.

Do not stop after scaffolding if the request asks for working CRUD. Do not leave
placeholder repositories, fake success responses, unregistered routes, or
untested error branches.

## Quality checklist

- [ ] The real API contract was followed without invented fields.
- [ ] Domain is independent of Gin/SQL drivers/env loading.
- [ ] DTO-to-entity mapping is explicit and safe.
- [ ] All HTTP routes go through the shared Gin engine and helpers.
- [ ] Errors are user-safe and retain useful typed kinds.
- [ ] Handlers contain no SQL or composition-root logic.
- [ ] DI and routes are complete in `internal/app`.
- [ ] Database choice from the generated profile is preserved.
- [ ] Unrelated files and user changes are untouched.
- [ ] Formatting and tests pass.
